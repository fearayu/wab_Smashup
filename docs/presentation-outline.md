# SMASHUP — โครงสร้างสไลด์นำเสนอ สอบหัวข้อ

> อิงคำแนะนำอาจารย์: *"ให้ทำสไลด์เรื่องของปัญหาก่อน • ต้องมีจุดยืนว่าทำไมทำแบบนี้ • present ว่า requirement คืออะไร function เป็นยังไง design ตอบโจทย์อย่างไร • ถ้าดีควรไปถึงขั้น test prototype"*

ลำดับสไลด์ตามนี้ (ประมาณ 15–20 นาที)

---

## สไลด์ 1 — ปัญหา (เริ่มที่นี่เสมอ)

```
- ที่มาที่ไป: ผู้เล่นแบดมือสมัครเล่นจองสนามต้องโทร/แชท ดูความว่างแบบ real-time ไม่ได้
- Pain point:
  1) เจอสนามเต็ม/กระจายข้อมูลกันคนละที่ (ปักคอร์ตต้องรอคำตอบ)
  2) หาคู่เล่น/คู่ซ้อมระดับใกล้เคียงยาก
  3) ข้อมูลการแข่ง/จัดคิวจัดการด้วยมือ (Excel, สายจับแบบมั่ว)
- Impact: ใครเจอปัญหา → ผู้เล่นทั่วไป, เจ้าของสนาม, ผู้จัดแข่ง
```

## สไลด์ 2 — Persona / กลุ่มผู้ใช้ (ต้องไปสัมผัสจริง)

- ผู้เล่นมือใหม่ — อยากได้คู่ซ้อม, กล้าไปสนามแรกยาก
- ผู้เล่นประจำ — ต้องการสนามว่าง/รอบที่ตรงกับตาราง
- เจ้าของสนาม/ผู้จัด — อยากได้ระบบยืนยัน/คิว/จัดแข่ง/รายงาน
- ⭐ หนึ่งสไลด์พาไป "ไปลงสนามจริง ได้เห็นกติกา ระดับมือ อย่างไร" (ใช้ User Testing ประกอบ)

## สไลด์ 3 — ความสำคัญของงาน (ทำไมต้องทำ)

- ลดภาระที่ผู้จัด/เจ้าของสนามต้องจัดการด้วยมือ
- เพิ่มประสบการณ์ผู้เล่น (ดูว่างได้เอง, หาคู่ตามระดับ/เวลา/ระยะทาง)
- เป็นฟีเจอร์ที่ "หลายที่ซื้อไปใช้ได้" (ขยายต่อยอด multi-venue ตามอาจารย์)

## สไลด์ 4 — Requirement (ใช้ docs/requirements-audit.md)

- FR-01…FR-15 (ตาราง) — เลือกเฉพาะที่สำคัญ 5-7 ข้อ
- 2 กระแสงานหลัก: **(A) จองสนาม/บริการ** และ **(B) หาคู่/นัดหมาย/แข่ง**
- NFR ที่ต้นแบบทำได้: ความถูกต้อง, สิทธิ์, หลายหน้าต่าง, ตรวจสอบย้อนหลัง

## สไลด์ 5 — User Flow (docs/user-flow.md, Mermaid)

- เริ่มอธิบายด้วย **Actor** (Guest/Player/Admin/Organizer)
- Flow จองสนามที่แก้ตามคำติ:
  > ยังไม่ล็อกอิน ดูได้ → กดจอง redirect ไปล็อกอิน `?next=` → จอง → รอผู้ดูแลยืนยัน → ชำระเงินหลังยืนยัน
- Flow แข่ง: สมัคร → **จัดสายตามระดับมือ (เก่งกระจาย ไม่ชนรอบแรก) + สุ่มสลับภายในระดับ** → เก็บผล → อันดับ 1/2/3

## สไลด์ 6 — จุดยืนของการออกแบบ (Protect ตัวเอง) ⭐

| คำถามกรรมการ | จุดยืน/เหตุผล |
|---|---|
| ทำไมจองแล้วไม่เก็บเงินทันที? | สนามแบดจริง ผู้เล่นโอน/จ่ายหน้างาน; สลิปเงินโอนหลังยืนยันเท่านั้นไม่รกขั้นตอน |
| ทำไมไม่ใช้ AI จับคู่? | ระดับผู้ยืนยันมีข้อมูลจำกัด; ใช้ deterministic scoring ตรวจสอบได้ ซื่อตรงต่อข้อมูล |
| ทำไมเก็บใน localStorage? | เป็นต้นแบบพิสูจน์ตรรกะ; มี seam API พร้อมสำหรับระบบจริง |
| ทำไมจัดสายตามระดับมือ? | ต้องการความยุติธรรม: มือเก่งเป็นหัวสายกระจายกัน ไม่เจอกันเองรอบแรก ยังคงสุ่มสลับภายในระดับเพื่อไม่เดาโครงสายได้ (ตามที่อาจารย์พูด: "แบ่งตามเลเวล → จับสลาก/สุ่ม → ชิงชนะเลิศ → อันดับ 1/2/3") |

## สไลด์ 7 — Function ที่ทำได้จริง (demo หลัก)

- จองสนาม (conflict check, 15 นาที, cancel ≥2 ชม.) — `booking/index.html`
- บุฟเฟต์ (เลขคิว, 30 คน/รอบ) — `booking/buffet-registration.html`
- จัดแข่ง/จัดสาย/อันดับ — `booking/tournament.html`
- หาคู่ + คำเชิญ + นัดหมาย — `matching/`, `appointments/`
- ผู้ดูแล: ยืนยัน/ยกเลิก/Admin dashboard — `admin/`
- แจ้งเตือนในแอป (bell) — runtime เดโม

## สไลด์ 8 — Design (ตอบโจทย์ requirement อย่างไร)

- กฎธุรกิจจุดเดียว `shared/*.js` (deep module) → ทุกหน้า/ทุกฝั่งใช้ร่วมกัน
- แยก flow: ดูได้ไม่ล็อกอิน vs จองต้องล็อกอิน — ตรง requirement
- responsive (Kanit + Space Grotesk, orange/black theme) สไตล์สนามแบด
- Accessibility: skip link, aria-label, focus order

## สไลด์ 9 — การทดสอบต้นแบบ (Test Prototype) ⭐

- Unit test: **10 ชุด / 210 จุดตรวจผ่านครบ** `node --test`
  - จองซ้ำ/คอนฟลิกต์, สิทธิ์เจ้าของ, การแข่ง/จัดสาย, การแจ้งเตือน
- Browser E2E: 33 ตรวจ (จอง/ผู้ดูแล/หาคู่/เชิญ/ตอบรับ/แจ้งเตือน/จัดสาย)
- **User Testing**: แผนใน `docs/user-testing-plan.md` (5–7 คน) → นำตัวเลข task success มาพูด

## สไลด์ 10 — ขอบเขตที่จริงใจ (ไม่ overclaim)

- ยังเป็นต้นแบบ localStorage ไม่ใช่ระบบ production
- ไม่มีชำระเงินจริง / ไม่มีอีเมล-LINE-Push / backend ยังไม่เชื่อม+deploy
- การจัดคิว/ยืนยันสถานะ/จัดการแข่งเป็นของ admin ในต้นแบบ
- → ปิดด้วย: แผนงานถัดไป (เชื่อม backend, user testing เพิ่ม, จัดทำระบบ payment)

## สไลด์ 11 — ทีมและการแบ่งงาน (ตอบอาจารย์เรื่อง "สปีดพาร์ท")

- Frontend (หน้า+UX) / Backend & Auth (API) / Domain Rules + Test & เล่ม
- กฎ: งานทุกชิ้นผ่าน `shared/` + ผ่าน test ก่อน merge (ดู PROJECT.md)
- ใครรับผิดชอบอะไร นำเสนอเป็นตาราง
