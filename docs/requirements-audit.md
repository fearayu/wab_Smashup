# Requirements Audit: SMASHUP Prototype

เอกสารนี้แยกข้อกำหนดที่ต้นแบบทำได้แล้วออกจากข้อกำหนดที่ต้องพัฒนาเพิ่ม เพื่อใช้ตรวจร่วมกับอาจารย์และป้องกันการเขียนขอบเขตเกินระบบจริง

## Functional requirements ที่ต้นแบบรองรับ

| รหัส | ข้อกำหนด | สถานะและหลักฐาน |
|---|---|---|
| FR-01 | ผู้ใช้สมัครและเข้าสู่ระบบได้ | มีใน `auth/` ใช้บัญชีผู้ใช้ใน localStorage |
| FR-02 | ผู้ใช้ประเมินระดับ ตอบคำถาม 6 ด้าน และบันทึกเป้าหมายได้ | มี `auth/player-assessment.html` |
| FR-03 | ผู้จัดตรวจและยืนยันระดับพร้อมชื่อ เหตุผล วัน จำนวนเกม และผลสังเกต | มีแบบฟอร์มผู้ดูแลและประวัติในแบบประเมิน |
| FR-04 | ระบบค้นหาคู่จากระดับ เวลา และระยะทาง | มี `matching/index.html` ใช้ `shared/match-core.js` คะแนน deterministic (ระดับ 70% เวลา 15% ระยะทาง 15%) ระดับยืนยันถูกใช้เป็นหลัก — **แก้แล้ว:** `levelRank` รองรับรหัสเต็ม (B/B+, A/Pro) ไม่หลุดเป็น rank 0 (ชุดทดสอบ `tests/match-core.test.cjs`) |
| FR-05 | ผู้ใช้เลือกหมายเลขคอร์ต วัน และเวลา | มี `booking/index.html` ใช้ `shared/service-rules.js` ตรวจคอร์ตซ้ำก่อนบันทึกทุกครั้ง (`booking/form.html` เป็นฟอร์มตัวอย่างแยก) — **แก้แล้ว:** กันวันย้อนหลัง/เกิน 7 วัน (`date.min`/`date.max`), กันยื่นคำขอยืนยันซ้ำช่วงเวลาเดียวกัน, แก้ `dateThai` ที่เคย ReferenceError และสถานะใหม่เป็น `รอตรวจสอบ` |
| FR-06 | แสดงรายการจองและสถานะของผู้ใช้ | มี `booking/my-bookings.html` รวมคอร์ต บุฟเฟต์ และคำขอบริการ |
| FR-07 | ผู้ใช้ยกเลิกรายการของตนเองตามเงื่อนไข | ตรวจเจ้าของรายการและเวลาล่วงหน้า 2 ชั่วโมง |
| FR-08 | ผู้ใช้ลงทะเบียนตีบุฟเฟต์และเลือกค่าลูก | flow หลัก `booking/buffet-registration.html`: โควตาต่อรอบ (`SLOT_CAPS` 20/15/15) แสดงจำนวนว่างสดบนหน้าจอ, กันรอบซ้ำ/เวลาทับซ้อน/กันกดซ้ำ (race guard); กฎกลาง `shared/service-rules.js` กันเต็ม 30 คนต่อรอบอีกชั้น — **แก้แล้ว** ในรอบนี้ |
| FR-09 | ผู้จัดยืนยัน/ยกเลิกรายการบุฟเฟต์และคำขอบริการ | มี `admin/index.html` และเก็บประวัติสถานะ — **แก้แล้ว:** ยืนยัน/ยกเลิกผ่านกฎกลาง `SmashRules.setStatus` จุดเดียวทุกหน้าผู้ดูแล (เดิมบางหน้าเขียน localStorage เอง) |
| FR-10 | แสดงรายชื่อเฉพาะวันและรอบ แล้วจัดคิวโดยผู้ดูแล | มี `regular-buffet-queue.html` แยกวัน/รอบและมือใหม่/รอบปกติ |
| FR-11 | สมัครแข่งขัน จองสนามซ้อม และส่งคำขอซื้อสินค้า | มีฟอร์มบริการและตรวจข้อมูลซ้ำ/จำนวน |
| FR-12 | รองรับหน้าจอมือถือและป้องกันการเลื่อนแนวนอนโดยไม่จำเป็น | ปรับแถบสถานะบัญชีและการ์ดรายการแล้ว ตารางที่ข้อมูลกว้างยังเลื่อนเฉพาะตาราง |
| FR-13 | จัดการแข่งขันแบบจับฉลากจัดสาย จนถึงรอบชิงและอันดับ 1/2/3 | มี `booking/tournament.html` + `shared/tournament.js` **จัดสายตามระดับมือ (seed เก่งกระจายสาย ไม่ชนรอบแรก)** แล้วสุ่มภายในระดับเดียวกัน, สร้าง Bracket (R32→R16→รอบรอง→ชิง), เลื่อนผู้ชนะขึ้นรอบ, คำนวณอันดับ — **แก้แล้ว:** ยกเลิกสมัครหลังจัดสายถูกปฏิเสธ (`cancelRegistration` กันเมื่อสถานะพ้น registration) (ชุดทดสอบ `tests/tournament.test.cjs` 37 ตรวจ) |
| FR-14 | แจ้งเตือนในแอปเมื่อมีเหตุการณ์สำคัญ | มี `shared/notifications.js` + `shared/notify-ui.js` ระฆังแจ้งเตือนใน header ทุกหน้า (หน้า user + หน้าย่อย admin): หลังจอง/สมัครแข่ง, ผู้ดูแลยืนยัน/ยกเลิก, ได้รับ-ตอบรับคำเชิญ, นับไม่ได้อ่าน — **แก้แล้ว:** `notify.clear(userId)` เคลียร์เป็นรายคน (เดิมล้างทั้งระบบ), ระฆัง path `../auth/` ถูกต้องบนหน้าย่อย (ชุดทดสอบ `tests/notifications.test.cjs` 20 ตรวจ) |
| FR-15 | ผู้ใช้ที่ยังไม่ล็อกอินดูตารางได้ แต่จองต้องล็อกอินก่อน | มีแบนเนอร์แจ้งเตือน login บน `booking/index.html` และ redirect ไป `auth/index.html?next=...` เมื่อกดจองโดยไม่ล็อกอิน |

## Non-functional requirements ที่กำหนดในต้นแบบ

| รหัส | ข้อกำหนด | ขอบเขตที่ตรวจได้ |
|---|---|---|
| NFR-01 | ความถูกต้องของข้อมูล | ตรวจชนิดข้อมูล วัน/เวลา เบอร์ จำนวน และสถานะก่อนบันทึก |
| NFR-02 | การควบคุมสิทธิ์ | ผู้ใช้แก้เฉพาะรายการตนเอง ผู้จัดจัดคิวและเปลี่ยนสถานะได้ |
| NFR-03 | ความสอดคล้องหลายหน้าต่าง | อ่านข้อมูลล่าสุด ตรวจบัญชี และใช้ Web Locks เมื่อเบราว์เซอร์รองรับ |
| NFR-04 | ตรวจสอบย้อนหลัง | รายการระดับและสถานะเก็บผู้ทำ เวลา เหตุผล และค่าเดิม/ใหม่เท่าที่ต้นแบบรองรับ |
| NFR-05 | ความเข้าใจง่าย | มีข้อความสถานะและเหตุผลที่ผู้ใช้ทำต่อได้ รวมข้อความเลื่อนตารางบนมือถือในหน้าที่ออกแบบไว้ |
| NFR-06 | ความปลอดภัยตามขอบเขตต้นแบบ | **แก้แล้ว:** stored XSS — ข้อความที่ผู้ใช้กรอกถูก escape ก่อน render ทุกจุด (admin/matching/queue/แจ้งเตือน); ยังเหลือข้อจำกัดเดิม: localStorage ถูกผู้ใช้เครื่องนั้นแก้ได้ ไม่ใช่การรักษาความปลอดภัยสำหรับระบบจริง |

## บันทึกการแก้ไขรอบพัฒนาล่าสุด (กันยายน 2026)

รายการด้านล่างคือสิ่งที่แก้/เพิ่มจริงในรอบนี้ เพื่อใช้ตอบกรรมการว่า “จุดอ่อนที่เคยพบถูกปิดแล้วหรือยัง”

### 1. บั๊ก 7 จุดที่แก้แล้ว

| จุดที่แก้ | รายละเอียด |
|---|---|
| match-core ranking | `levelRank` ไม่มี alias สำหรับรหัสเต็ม (B/B+, A/Pro) เคยหลุดเป็น rank 0 → เพิ่ม mapping แล้ว |
| booking.js | `dateThai` ReferenceError, `date.max` กันวันเกิน 7 วัน, กันยื่นซ้ำช่วงเวลาเดียวกัน, สถานะใหม่เป็น `รอตรวจสอบ` |
| admin workflow | ยืนยัน/ยกเลิกผ่าน `SmashRules.setStatus` (กฎกลาง) เหมือนกันทุกหน้าผู้ดูแล |
| admin-dashboard | หน้าลึก `admin/admin-dashboard.html` ถูกซ่อนออกจากเมนูทั้งหมด (ไม่มีการลิงก์อ้างอิงแล้ว) |
| notify-ui.js | เส้นทาง `../auth/index.html` ถูกต้องบนหน้าในโฟลเดอร์ย่อย (booking/matching/appointments/admin) |
| stored XSS | escape ข้อความผู้ใช้ก่อน render ใน admin/matching/queue/แจ้งเตือน (3+ ไฟล์) + quote ในลิงก์แจ้งเตือน |
| buffet-registration | เพิ่ม `SLOT_CAPS` (20/15/15) แสดงจำนวนว่างสด + กันกดซ้ำ (race guard) |

### 2. พฤติกรรมที่แก้ให้ตรงกฎ

- `SmashNotify.clear()` เคลียร์**รายคน** (เดิมล้างการแจ้งเตือนทั้งระบบ)
- `cancelRegistration` ปฏิเสธการยกเลิกสมัครแข่ง**หลังจากจัดสาย (buildBracket) แล้ว** (เดิมยกเลิกเงียบ ๆ ได้)

### 3. การทดสอบที่เพิ่ม/ยืนยัน

- unit tests: **10 ชุด / 210 จุดตรวจผ่านครบ** (`node --test tests/*.test.cjs`) — เพิ่ม `appointments-expiry` (การหมดอายุคำเชิญ 7 วัน), ขยาย `concurrency` (จองชนกัน/race), `tournament` (state machine hardening), `service-rules` (practice-court branch), `notifications` (clear รายคน)
- Browser E2E: **33 ตรวจผ่านครบ** (`npm run e2e`) — ครอบคลุมจอง/ซ้ำ/ยกเลิก, ผู้ดูแล, หาคู่/เชิญ/ตอบรับ, แจ้งเตือน, จัดสายตามระดับ

### 4. Backend (จุดเชื่อมต่อ API)

- **ทำแล้ว:** notifications CRUD ครบ 5 routes (`GET /api/v1/notifications`, `GET /unread-count`, `POST /`, `POST /read-all`, `POST /:id/read`) — โค้ดครบ (entity/repo D1+memory/service/handler/schema/router) + D1 migration `0004_create_notifications.sql`
- **กำลังทำ:** profiles endpoints 4 routes (`GET/PUT me`, `GET public/:id`, `GET list admin-only`) — handler + D1 repo เขียนแล้ว แต่ `userService.updateProfile` ยังไม่เสร็จ → **typecheck ยังไม่ผ่านชั่วคราว (4 จุด)**
- **ยังไม่มี:** endpoints สำหรับ tournament / appointments / buffet / matchmaking (ข้อมูลฝั่งหน้าเว็บยังอยู่ใน `shared/*.js` + localStorage)

### 5. การตัดสินใจ Phase 0 (ขอบเขตสาธิต)

- สาธิตเป็น **สนามเดียว (single-venue)** กับผู้จัดกลาง — backend ยังมี schema หลายสนาม (owner→venue→court) เก็บไว้เป็นเรื่องต่อยอด ไม่ใช่ขอบเขตของต้นแบบฉบับนี้

## ข้อกำหนดที่อาจารย์ควรตัดสินใจก่อนเขียนว่า “ระบบมี”

| ประเด็น | สถานะปัจจุบัน | ถ้าต้องส่งมอบเป็นระบบจริงต้องเพิ่ม |
|---|---|---|
| ฐานข้อมูลกลาง | หน้าเว็บยังใช้ localStorage โหมดเดโม — backend Hono+D1 มี auth/users/venues/courts/slots/bookings/payments/notifications แล้ว แต่**หน้าเว็บยังไม่เชื่อม API** | เชื่อมหน้าเว็บเข้ากับ API, ธุรกรรมจองซ้ำ และ backup |
| การชำระเงิน | ไม่มีการรับเงินจริง | payment gateway, webhook, ใบเสร็จ, คืนเงิน |
| การแจ้งเตือน | มีแจ้งเตือน **ในแอป** (`shared/notifications.js`) — ยังไม่มีอีเมล/LINE/Push | ช่องทางแจ้งเตือนภายนอก สถานะส่งสำเร็จ และการตั้งค่าผู้ใช้ |
| การจัดการแข่ง | มี single-elimination + **จัดสายตามระดับมือ + สุ่มภายในระดับ** + อันดับในต้นแบบ | point system, รอบพบกันหมด (round-robin), สถิติผู้เล่นย้อนหลัง, ระบบผลแข่งที่ผู้เล่นยืนยันได้ |
| เจ้าของสนามหลายสาขา | ยังไม่แยกสิทธิ์ | venue/branch, owner role และสิทธิ์ตามสนาม |
| นัดหมาย/คำเชิญระหว่างผู้เล่น | มีแล้วสำหรับต้นแบบ: `shared/appointments.js` ส่งคำเชิญผูกกับ id ผู้รับ ยืนยัน/ปฏิเสธ/ยกเลิก หมดอายุ 7 วัน มีชุดทดสอบ (`tests/appointments.test.cjs`) แต่ไม่ได้จองคอร์ตจริงและไม่มีการแจ้งเตือนภายนอก | appointment บนเซิร์ฟเวอร์, แจ้งเตือนอีเมล/LINE/Push, reschedule และความถูกต้องพร้อมกันหลายอุปกรณ์ |
| การร้องเรียนระดับ/คู่เล่น | ยังไม่มีหลักฐานร่วมเกม | report, moderation, หลักฐาน และกระบวนการอุทธรณ์ |
| รายงานเชิงธุรกิจ | Dashboard เป็นข้อมูลรายการ | รายได้จริง การใช้คอร์ต occupancy export และช่วงเวลา |
| บัญชีและข้อมูลส่วนบุคคล | บัญชีจำลองในเครื่อง | hash ฝั่งเซิร์ฟเวอร์, reset password, verify contact, session expiry, privacy/consent |
| การทดสอบผู้ใช้ | ทดสอบกฎและหน้าจอเบื้องต้น | test plan, กลุ่มตัวอย่าง, task success, usability, accessibility และผลการทดสอบ |

## ข้อความขอบเขตสำหรับใช้ในรายงาน

SMASHUP ฉบับนี้เป็นเว็บต้นแบบฝั่งผู้ใช้และผู้ดูแลสำหรับสาธิตการประเมินระดับ การเปรียบเทียบผู้เล่น การเลือกคอร์ต การลงทะเบียนบุฟเฟต์ การจัดคิว และการจัดการคำขอบริการ ข้อมูลเก็บใน localStorage ของเบราว์เซอร์ จึงใช้สาธิตขั้นตอนและการแสดงผลได้ แต่ยังไม่รวมฐานข้อมูลกลาง การชำระเงินจริง การแจ้งเตือนภายนอก การยืนยันตัวตนบนเซิร์ฟเวอร์ และการจองพร้อมกันหลายอุปกรณ์

การจับคู่เป็นคะแนนเปรียบเทียบจากข้อมูลที่ผู้ใช้กรอก ระดับที่ผู้จัดยืนยัน และเวลา/ระยะทางที่ระบุ ไม่ใช่การรับรองฝีมือหรือการรับประกันว่าจะนัดหมายสำเร็จ การจัดคิวและการยืนยันสถานะเป็นหน้าที่ผู้จัดในต้นแบบ
