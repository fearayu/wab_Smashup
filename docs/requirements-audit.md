# Requirements Audit: SMASHUP Prototype

เอกสารนี้แยกข้อกำหนดที่ต้นแบบทำได้แล้วออกจากข้อกำหนดที่ต้องพัฒนาเพิ่ม เพื่อใช้ตรวจร่วมกับอาจารย์และป้องกันการเขียนขอบเขตเกินระบบจริง

## Functional requirements ที่ต้นแบบรองรับ

| รหัส | ข้อกำหนด | สถานะและหลักฐาน |
|---|---|---|
| FR-01 | ผู้ใช้สมัครและเข้าสู่ระบบได้ | มีใน `auth/` ใช้บัญชีผู้ใช้ใน localStorage |
| FR-02 | ผู้ใช้ประเมินระดับ ตอบคำถาม 6 ด้าน และบันทึกเป้าหมายได้ | มี `auth/player-assessment.html` |
| FR-03 | ผู้จัดตรวจและยืนยันระดับพร้อมชื่อ เหตุผล วัน จำนวนเกม และผลสังเกต | มีแบบฟอร์มผู้ดูแลและประวัติในแบบประเมิน |
| FR-04 | ระบบค้นหาคู่จากระดับ เวลา และระยะทาง | มี `matching/index.html` ใช้ `shared/match-core.js` คะแนน deterministic (ระดับ 70% เวลา 15% ระยะทาง 15%) ระดับยืนยันถูกใช้เป็นหลัก |
| FR-05 | ผู้ใช้เลือกหมายเลขคอร์ต วัน และเวลา | มี `booking/index.html` ใช้ `shared/service-rules.js` ตรวจคอร์ตซ้ำก่อนบันทึกทุกครั้ง (`booking/form.html` เป็นฟอร์มตัวอย่างแยก) |
| FR-06 | แสดงรายการจองและสถานะของผู้ใช้ | มี `booking/my-bookings.html` รวมคอร์ต บุฟเฟต์ และคำขอบริการ |
| FR-07 | ผู้ใช้ยกเลิกรายการของตนเองตามเงื่อนไข | ตรวจเจ้าของรายการและเวลาล่วงหน้า 2 ชั่วโมง |
| FR-08 | ผู้ใช้ลงทะเบียนตีบุฟเฟต์และเลือกค่าลูก | มี `regular-buffet-booking.html` ตรวจซ้ำ เต็มรอบ และเวลาทับซ้อน |
| FR-09 | ผู้จัดยืนยัน/ยกเลิกรายการบุฟเฟต์และคำขอบริการ | มี `admin/index.html` และเก็บประวัติสถานะ |
| FR-10 | แสดงรายชื่อเฉพาะวันและรอบ แล้วจัดคิวโดยผู้ดูแล | มี `regular-buffet-queue.html` แยกวัน/รอบและมือใหม่/รอบปกติ |
| FR-11 | สมัครแข่งขัน จองสนามซ้อม และส่งคำขอซื้อสินค้า | มีฟอร์มบริการและตรวจข้อมูลซ้ำ/จำนวน |
| FR-12 | รองรับหน้าจอมือถือและป้องกันการเลื่อนแนวนอนโดยไม่จำเป็น | ปรับแถบสถานะบัญชีและการ์ดรายการแล้ว ตารางที่ข้อมูลกว้างยังเลื่อนเฉพาะตาราง |

## Non-functional requirements ที่กำหนดในต้นแบบ

| รหัส | ข้อกำหนด | ขอบเขตที่ตรวจได้ |
|---|---|---|
| NFR-01 | ความถูกต้องของข้อมูล | ตรวจชนิดข้อมูล วัน/เวลา เบอร์ จำนวน และสถานะก่อนบันทึก |
| NFR-02 | การควบคุมสิทธิ์ | ผู้ใช้แก้เฉพาะรายการตนเอง ผู้จัดจัดคิวและเปลี่ยนสถานะได้ |
| NFR-03 | ความสอดคล้องหลายหน้าต่าง | อ่านข้อมูลล่าสุด ตรวจบัญชี และใช้ Web Locks เมื่อเบราว์เซอร์รองรับ |
| NFR-04 | ตรวจสอบย้อนหลัง | รายการระดับและสถานะเก็บผู้ทำ เวลา เหตุผล และค่าเดิม/ใหม่เท่าที่ต้นแบบรองรับ |
| NFR-05 | ความเข้าใจง่าย | มีข้อความสถานะและเหตุผลที่ผู้ใช้ทำต่อได้ รวมข้อความเลื่อนตารางบนมือถือในหน้าที่ออกแบบไว้ |
| NFR-06 | ความปลอดภัยตามขอบเขตต้นแบบ | ป้องกันการกดผิดจากหน้าจอ แต่ localStorage ถูกผู้ใช้เครื่องนั้นแก้ได้ ไม่ใช่การรักษาความปลอดภัยสำหรับระบบจริง |

## ข้อกำหนดที่อาจารย์ควรตัดสินใจก่อนเขียนว่า “ระบบมี”

| ประเด็น | สถานะปัจจุบัน | ถ้าต้องส่งมอบเป็นระบบจริงต้องเพิ่ม |
|---|---|---|
| ฐานข้อมูลกลาง | ยังไม่มี ใช้ localStorage | API/ฐานข้อมูล ธุรกรรมจองซ้ำ และ backup |
| การชำระเงิน | ไม่มีการรับเงินจริง | payment gateway, webhook, ใบเสร็จ, คืนเงิน |
| การแจ้งเตือน | ไม่มีอีเมล/LINE/Push | ช่องทางแจ้งเตือน สถานะส่งสำเร็จ และการตั้งค่าผู้ใช้ |
| เจ้าของสนามหลายสาขา | ยังไม่แยกสิทธิ์ | venue/branch, owner role และสิทธิ์ตามสนาม |
| นัดหมาย/คำเชิญระหว่างผู้เล่น | มีแล้วสำหรับต้นแบบ: `shared/appointments.js` ส่งคำเชิญผูกกับ id ผู้รับ ยืนยัน/ปฏิเสธ/ยกเลิก หมดอายุ 7 วัน มีชุดทดสอบ (`tests/appointments.test.cjs`) แต่ไม่ได้จองคอร์ตจริงและไม่มีการแจ้งเตือนภายนอก | appointment บนเซิร์ฟเวอร์, แจ้งเตือนอีเมล/LINE/Push, reschedule และความถูกต้องพร้อมกันหลายอุปกรณ์ |
| การร้องเรียนระดับ/คู่เล่น | ยังไม่มีหลักฐานร่วมเกม | report, moderation, หลักฐาน และกระบวนการอุทธรณ์ |
| รายงานเชิงธุรกิจ | Dashboard เป็นข้อมูลรายการ | รายได้จริง การใช้คอร์ต occupancy export และช่วงเวลา |
| บัญชีและข้อมูลส่วนบุคคล | บัญชีจำลองในเครื่อง | hash ฝั่งเซิร์ฟเวอร์, reset password, verify contact, session expiry, privacy/consent |
| การทดสอบผู้ใช้ | ทดสอบกฎและหน้าจอเบื้องต้น | test plan, กลุ่มตัวอย่าง, task success, usability, accessibility และผลการทดสอบ |

## ข้อความขอบเขตสำหรับใช้ในรายงาน

SMASHUP ฉบับนี้เป็นเว็บต้นแบบฝั่งผู้ใช้และผู้ดูแลสำหรับสาธิตการประเมินระดับ การเปรียบเทียบผู้เล่น การเลือกคอร์ต การลงทะเบียนบุฟเฟต์ การจัดคิว และการจัดการคำขอบริการ ข้อมูลเก็บใน localStorage ของเบราว์เซอร์ จึงใช้สาธิตขั้นตอนและการแสดงผลได้ แต่ยังไม่รวมฐานข้อมูลกลาง การชำระเงินจริง การแจ้งเตือนภายนอก การยืนยันตัวตนบนเซิร์ฟเวอร์ และการจองพร้อมกันหลายอุปกรณ์

การจับคู่เป็นคะแนนเปรียบเทียบจากข้อมูลที่ผู้ใช้กรอก ระดับที่ผู้จัดยืนยัน และเวลา/ระยะทางที่ระบุ ไม่ใช่การรับรองฝีมือหรือการรับประกันว่าจะนัดหมายสำเร็จ การจัดคิวและการยืนยันสถานะเป็นหน้าที่ผู้จัดในต้นแบบ
