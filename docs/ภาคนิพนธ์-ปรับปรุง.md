## กิตติกรรมประกาศ

โครงงานฉบับนี้สำเร็จลุล่วงไปด้วยดี เนื่องด้วยความกรุณาและการให้คำปรึกษาแนะนำเป็นอย่างดียิ่งจาก ผู้ช่วยศาสตราจารย์ ดร.สุรางคนา ระวังยศ อาจารย์ที่ปรึกษาโครงงาน ที่ได้สละเวลาอันมีค่าในการถ่ายทอดความรู้ ให้ข้อเสนอแนะ และตรวจสอบความถูกต้องของเนื้อหาตลอดระยะเวลาการดำเนินงาน

คณะผู้จัดทำขอกราบขอบพระคุณเป็นอย่างสูง และขอขอบคุณคณะเทคโนโลยีสารสนเทศ มหาวิทยาลัยพะเยา ที่เอื้อเฟื้อสถานที่และอุปกรณ์สำหรับการศึกษาค้นคว้า

## บทที่ 1 บทนำ

### ที่มาและความสำคัญของโครงงาน

แบดมินตันเป็นกีฬาที่ได้รับความนิยมอย่างแพร่หลายในประเทศไทย ทั้งในระดับนันทนาการและเชิงแข่งขัน มีผู้เล่นจำนวนมากที่ต้องการเล่นอย่างสม่ำเสมอ แต่ผู้เล่นมักพบปัญหา 2 อย่างที่เกิดร่วมกัน

**ปัญหาที่หนึ่ง: การหาคู่เล่นหรือคู่ต่อสู้ที่มีระดับฝีมือใกล้เคียงกัน**
ผู้เล่นมือใหม่ไปจนถึงมือกลาง มักหาคู่นักตีที่ไม่ได้เก่งหรืออ่อนจนเกินไปไม่ได้ และต้องตรงกับเวลาว่างของทั้งสองฝ่าย ทำให้ต้องยกเลิกการเล่นหรือเสียเวลารอคอย

**ปัญหาที่สอง: การจองสนามที่ยังไม่มีประสิทธิภาพ**
การจองสนามแบบดั้งเดิมอาศัยการโทรศัพท์หรือพิมพ์ข้อความในแอปพลิเคชันแชท ไม่สามารถเห็นความว่างของคอร์ตแบบทันที ส่งผลให้มีการจองซ้ำหรือเข้าใจความว่างผิดพลาด

จากปัญหาดังกล่าว คณะผู้จัดทำจึงพัฒนาต้นแบบ (Prototype) ของ **"ระบบจองสนามแบดมินตันและช่วยค้นหาคู่เล่นตามระดับฝีมือและเวลาว่าง"** ซึ่งเป็นเว็บต้นแบบที่รวมสองกระแสงานหลักไว้ในระบบเดียว:
1. ระบบจองสนาม (จองคอร์ต ว่าง/หลุม ตรวจความว่างก่อนบันทึก)
2. ระบบช่วยค้นหาคู่เล่น (ประเมินระดับ → คำนวณคะแนนความตรง → นัดหมาย/ส่งคำเชิญ)

ระบบนี้จัดทำเป็นเว็บต้นแบบโดยเก็บข้อมูลในเบราว์เซอร์ (localStorage) พร้อมกฎกลางที่ทดสอบได้ เพื่อสาธิตแนวคิดและขั้นตอนการทำงานจริง ก่อนนำไปพัฒนาเป็นระบบที่ใช้ฐานข้อมูลกลางและเซิร์ฟเวอร์ต่อไป

---

### วัตถุประสงค์ของโครงงาน

1. เพื่อพัฒนาเว็บต้นแบบสำหรับจองสนามแบดมินตันที่ตรวจความว่างของคอร์ตก่อนบันทึก และให้ผู้ใช้ดู/ยกเลิกรายการของตนเองได้ตามเงื่อนไข
2. เพื่อพัฒนาระบบช่วยค้นหาคู่เล่นที่ใช้ระดับฝีมือ เวลาที่สะดวก และระยะทาง โดยให้คะแนนความตรงอย่างเป็นระบบและโปร่งใส (แสดงเหตุผลและที่มาของระดับ)
3. เพื่อพัฒนาระบบนัดหมาย/ส่งคำเชิญระหว่างผู้เล่นที่ผูกกับตัวตนของผู้รับอย่างถูกต้อง
4. เพื่อสร้างชุดทดสอบอัตโนมัติ (7 ชุด/116 จุดตรวจ) ครอบคลุมกฎการจอง ความถูกต้องของสิทธิ์ และความซื่อตรงของคะแนนจับคู่

---

### ขอบเขตของการศึกษา

การพัฒนาระบบในครั้งนี้เป็น**เว็บต้นแบบสำหรับการสาธิต** (Prototype) เก็บข้อมูลใน localStorage ของเบราว์เซอร์ กำหนดกลุ่มผู้ใช้งาน 3 กลุ่มหลัก

#### 1. ผู้เล่น (Player)
- สมัครสมาชิกและเข้าสู่ระบบ (บัญชีจำลองในเครื่อง)
- ประเมินระดับฝีมือด้วยแบบสอบถาม 6 ด้าน (ระดับ N ถึง A/Pro) และให้ผู้จัดตรวจยืนยัน
- จองคอร์ตแบบเลือกวัน/เวลา/หมายเลขคอร์ต ตรวจการจองซ้ำก่อนบันทึก ดูและยกเลิกรายการของตนตามเงื่อนไข (ก่อนเริ่มอย่างน้อย 2 ชั่วโมง)
- ค้นหาคู่เล่นจากระดับ เวลา ระยะทาง รูปแบบ และส่งคำเชิญนัดหมาย ยืนยัน/ปฏิเสธได้

#### 2. ผู้จัด/เจ้าของสนาม (Court Owner/Organizer)
- ยืนยันหรือยกเลิกรายการจอง บุฟเฟต์ และคำขอบริการ พร้อมประวัติสถานะ
- ตรวจและยืนยันระดับผู้เล่น (บันทึกชื่อผู้ประเมิน วันที่สังเกต จำนวนเกม ผลสังเกต และหลักฐานสำหรับระดับสูง)
- จัดคิวผู้เล่นบุฟเฟต์ตามวัน/รอบ และดูภาพรวมจำนวนรายการ/รายได้จากการจองยืนยัน

#### 3. ผู้ดูแลระบบ (System Administrator)
- จัดการบัญชีและสิทธิ์ (หน้า `admin/`) ผ่านบัญชีแอดมินจำลอง

#### ขอบเขตด้านเทคนิค
- หน้าเว็บ: Static HTML/CSS/JavaScript ภาษาไทยเป็นหลัก ใช้กฎกลาง `shared/*.js` ที่รันได้ทั้งในเบราว์เซอร์และ Node
- ทดสอบอัตโนมัติ: Node.js test runner (`node --test tests/*.test.cjs` จำนวน 116 รายการ ผ่านครบ) + ทดสอบผ่านหน้าจอ Browser E2E (`tests/e2e/run-e2e.mjs` 24 รายการ ผ่านครบ)
- Backend (จัดทำโค้ด Hono + Cloudflare Workers/D1/KV ไว้ ทำให้ตรวจผ่าน typecheck/build/smoke แล้ว) แต่**ยังไม่ได้เชื่อมต่อกับหน้าเว็บ** และยังไม่ได้ deploy

#### สิ่งที่อยู่นอกขอบเขตของต้นแบบนี้
- ฐานข้อมูลกลาง/การจองพร้อมกันหลายอุปกรณ์ (วันนี้ใช้ localStorage หนึ่งเครื่องต่อเบราว์เซอร์)
- การชำระเงินจริง (การล็อก 15 นาทีเป็นเพียงขั้นตอนจำลองการรอผู้จัดยืนยัน)
- การแจ้งเตือนอีเมล/LINE/Push และการยืนยันตัวตน/สิทธิ์บนเซิร์ฟเวอร์
- การรับรองระดับฝีมือ (คะแนน/ระดับเป็นข้อมูลรายงานตนเองที่ผู้จัดยืนยัน — ไม่ใช่การรับรองระดับประเทศ)

---

### ประโยชน์ที่คาดว่าจะได้รับ

1. **ได้เว็บต้นแบบจองสนามที่ตรวจความว่างอย่างถูกต้อง** — ลดการจองซ้ำ และผู้ใช้ตรวจสอบ/ยกเลิกรายการของตนเองได้โดยไม่ต้องโทรหาเจ้าของสนาม
2. **ได้ระบบช่วยค้นหาคู่เล่นที่อธิบายได้** — ผู้ใช้เห็นคะแนน เหตุผล และที่มาของระดับ จึงเข้าใจว่าทำไมระบบจึงแนะนำคู่รายนี้ และไม่หลอกด้วยข้อมูลปลอม
3. **ได้ชุดทดสอบที่ใช้ประกอบการตรวจโครงงานจริง** — ผลการทดสอบกฎเดิมและกฎใหม่ปรากฏเป็นหลักฐานเชิงวัตถุ ไม่ใช่คำกล่าวอ้าง
4. **ได้แนวทางการต่อยอด** — โครงสร้างแยกกฎธุรกิจออกจากหน้าจอ ทำให้ย้ายไปใช้ฐานข้อมูลกลาง/เซิร์ฟเวอร์ได้โดยไม่ต้องเขียนหน้าใหม่

### ขั้นตอนการดำเนินงาน

#### 1. การศึกษาข้อมูลและวิเคราะห์ความต้องการ (สัปดาห์ที่ 1–2)
- ศึกษาแนวคิดการประเมินระดับผู้เล่นแบดมินตัน (เรียงระดับตามคำอธิบายพฤติกรรม ใช้ในต้นแบบเท่านั้น)
- ศึกษาแอปพลิเคชันจองสนามและหาคู่เล่นที่มีอยู่ เพื่อกำหนดจุดที่ต้องสาธิต
- ตั้งคำถามตรวจระบบ (ดู `docs/system-review-questions.md`) เพื่อใช้สอบอาจารย์และตรวจขอบเขต

#### 2. การออกแบบระบบ (สัปดาห์ที่ 3–4)
- ออกแบบ Flow A (จองสนาม) และ Flow B (หาคู่เล่น/นัดหมาย) พร้อมกฎธุรกิจที่ต้องตรวจ
- ออกแบบกฎกลาง (`shared/*.js`) ให้รันได้ทั้งเบราว์เซอร์และ Node เพื่อให้ทดสอบอัตโนมัติได้
- ออกแบบหน้าจอตามโทนสีส้ม/ดำ/ขาว รองรับมือถือและเดสก์ท็อป

#### 3. การพัฒนาระบบ (สัปดาห์ที่ 5–9)
- พัฒนา Shared Domain Modules + หน้าจอผู้ใช้และผู้ดูแล
- พัฒนาสูตรคะแนนจับคู่ที่แน่นอน (deterministic) และระบบคำเชิญนัดหมายผูก id ผู้รับ
- พัฒนา backend (Hono + Cloudflare Workers/D1/KV) และตรวจให้ผ่าน typecheck/build/smoke

#### 4. การทดสอบระบบ (สัปดาห์ที่ 10–12)
- ทดสอบอัตโนมัติ 116 จุดตรวจ (7 ชุด): กฎการจอง ความถูกต้องของผู้มีสิทธิ์ สถานะสิ้นสุด โหมด API ปลอดภัย และความซื่อตรงของคะแนน
- ทดสอบหน้าจอด้วยตนเองตาม Flow A/B และปรับปรุงตามข้อสังเกต
- (ข้อเสนอ) ทำการทดสอบผู้ใช้จริงก่อนสรุปผล ในรายงานนี้ยังไม่มีผลการทดลองผู้ใช้จริง

#### 5. การสรุปและนำเสนอ (สัปดาห์ที่ 13)
- จัดทำเอกสารภาคนิพนธ์และเอกสารสนับสนุนการตรวจ (README, PROJECT, requirements audit, ระบบตรวจคำถาม)
- จัดทำวิธีการสาธิตและขอบเขตที่ตรงกับระบบจริง

### เครื่องมือที่ใช้ในการพัฒนาโปรแกรม

#### ฮาร์ดแวร์ (Hardware)
1. คอมพิวเตอร์สำหรับพัฒนา (CPU รุ่นปัจจุบัน, RAM อย่างน้อย 8 GB)
2. อุปกรณ์ทดสอบ: สมาร์ทโฟน (Android/iOS) และคอมพิวเตอร์เดสก์ท็อป/โน้ตบุ๊ก

#### ซอฟต์แวร์และเครื่องมือพัฒนา (Software & Development Tools)

1. Environment และ IDE
   - Visual Studio Code (Editor หลัก)
   - Git และ GitHub (Version Control)
   - PowerShell / Node.js v24 สำหรับรันและทดสอบ

2. เทคโนโลยีหลัก
   - HTML5 + CSS3 + JavaScript แบบ Static (หน้าเว็บต้นแบบ, ภาษาไทยหลัก)
   - Shared Domain Modules ภาษา JavaScript (รันได้ทั้งเบราว์เซอร์และ Node)
   - Node.js test runner สำหรับชุดทดสอบอัตโนมัติ
   - Hono (TypeScript) + Cloudflare Workers/D1/KV สำหรับ backend (มีโค้ด, ยังไม่เชื่อมหน้าเว็บ)

## บทที่ 2 เอกสารและงานวิจัยที่เกี่ยวข้อง

### ทฤษฎีและหลักการที่เกี่ยวข้อง

#### Client-Server และ Web Application
ต้นแบบนี้เป็น Web Application ที่ทำงานบนเบราว์เซอร์ ฝั่งหน้าบ้านจัดการอินเทอร์เฟซและกฎการใช้งาน ฝั่งเบราว์เซอร์เก็บข้อมูลชั่วคราว (localStorage) แล้วออกแบบ API seam ไว้สำหรับฝั่งเซิร์ฟเวอร์ในภายหลัง แนวคิด Client–Server และ Stateless API (REST/RESTful) ใช้เป็นพื้นฐานในการออกแบบ API ของ backend (`backend/`)

#### หลักการตรวจความถูกต้องก่อนบันทึก (Validation before commit)
ระบบจองสนามต้องป้องกันการจองซ้ำและข้อมูลผิดรูปแบบ ต้นแบบนี้รวมกฎไว้ที่ชั้นกลาง (`shared/service-rules.js`) เพื่อให้ทุกหน้าตรวจแบบเดียวกัน: ตรวจวัน/เวลา เบอร์โทร จำนวน ผู้มีสิทธิ์ และตรวจการชนกันของคอร์ตอีกครั้งก่อนเขียนข้อมูลเสมอ อีกทั้งเมื่อเบราว์เซอร์รองรับ Web Locks จะจัดลำดับการเขียนระหว่างหน้าต่างใน origin เดียวกัน

#### หลักการทำ Systems of Record แบบ Single Source of Truth
การให้ทุกหน้าและผู้ใช้ทุกบทบาทอ่าน/เขียนผ่านกฎกลางจุดเดียว ช่วยให้การตีความสถานะ (เช่น รายการรอตรวจที่หมดเวลาแล้วถือเป็นยกเลิก) ตรงกันทั้งระบบ และเอื้อต่อการทดสอบอัตโนมัติด้วย Node

### งานวิจัย/แนวคิดที่เกี่ยวข้อง

#### 1. แนวคิดการเรียงลำดับระดับผู้เล่นแบดมินตัน
โครงงานใช้แนวคิดการเรียงระดับแบบกว้าง (N, S/BG, P-, P, P+, C, C+, B/B+, A/Pro) พร้อมคำอธิบายพฤติกรรม และกำหนดให้ระดับที่ใช้ในการค้นหาคู่เป็นระดับที่ผู้จัดยืนยันแล้ว (หรือระบุอย่างชัดเจนว่ายังไม่ยืนยัน) ระดับเป็นเพียงข้อมูลรายงานตนเอง+การสังเกต ไม่ใช่การรับรองอย่างเป็นทางการ

#### 2. แนวคิดการจองระบบเรียลไทม์และแก้ไขความขัดแย้ง
ระบบจองสนามทั่วไปต้องมีกลไกแก้ไขเมื่อผู้ใช้จองคอร์ตเดียวกันในเวลาเดียวกันพร้อมกัน ต้นแบบนี้จึงตรวจข้อมูลล่าสุดก่อนเขียนทุกครั้ง และใช้ Web Locks เมื่อเบราว์เซอร์รองรับซึ่งเป็นการจำลองแนวคิดการล็อก/ธุรกรรมของระบบจริง (ดู `tests/concurrency.test.cjs`)

#### 3. แนวคิดการให้คะแนนจับคู่ที่อธิบายได้ (Interpretable Matching Score)
แทนที่จะใช้ "ความลับ" หรือโมเดล AI ที่อธิบายไม่ได้ ต้นแบบนี้ใช้สูตรแน่นอนที่ตรวจสอบได้: ระดับ 70% + ความใกล้เคียงเวลาที่สะดวก 15% + ระยะทาง 15% และแสดงเหตุผลแต่ละข้อบนการ์ดผู้เล่น ทั้งนี้เป็นค่าทดลอง ไม่ใช่การรับประกันผลการนัดหมาย

### รีวิวแอปพลิเคชัน

#### 1. แอปพลิเคชัน/บริการจองสนาม (Court booking services)
บริการจองสนามทั่วไปโฟกัสที่การแสดงความว่าง การจอง และการชำระเงิน แต่ส่วนใหญ่แยกข้อมูลผู้เล่นระดับฝีมือ: ผู้เล่นต้องรู้จักกันก่อนจึงจะเล่นเป็นคู่ได้

**จุดที่ต้นแบบนี้เน้น**: เชื่อมลูปการจอง (Flow A) เข้ากับลูปการหาคู่ (Flow B) เพื่อปิดช่องว่าง "จองสนามได้แต่ไม่มีคู่เล่น"

#### 2. แพลตฟอร์มหาคู่เล่น/จัดกลุ่ม (Player matching communities)
แพลตฟอร์มหาคู่เล่นนิยมใช้การประกาศกลุ่มหรือการอนุมัติโดยผู้จัด แต่ระดับที่ใช้มักเป็นค่าที่ผู้ใช้ระบุเองโดยไม่มีการยืนยัน

**จุดที่ต้นแบบนี้เพิ่ม**: ระบบแสดงที่มาของระดับ (ผู้จัดยืนยัน/ประเมินเอง) ให้คะแนนที่คำนวณได้ และให้ส่งคำเชิญที่ผูกกับตัวตนผู้รับจริง ไม่ใช่แค่ชื่อที่พิมพ์
