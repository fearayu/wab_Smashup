# SMASHUP — User Testing Plan (ทดสอบต้นแบบกับผู้ใช้จริง)

> อาจารย์: *"ต้องเข้าใจยูเซอร์จริงๆ…การดูเฉยๆ อาจไม่รู้ จึงควรเอาตัวไปลง เช่น ไปตีแบด ดูกลุ่มผู้เล่นว่าเป็นระดับไหน"* และ *"ถ้าดีควรไปถึงขั้น test prototype"*

เอกสารนี้คือแผนทดสอบต้นแบบกับผู้ใช้จริง **ก่อนการสอบหัวข้อ** เพื่อมีหลักฐานว่า flow และตรรกะ make sense กับคนใช้งานจริง

---

## 1. เป้าหมายของรอบทดสอบ

1. ตรวจว่า **User Flow ใช้ได้จริง** กับคนที่ไม่รู้ระบบ (ตามคำติอาจารย์เรื่องตรรกะหน้าจอง)
2. เก็บ **หลักฐานยืนยัน** ว่าเข้าใจง่าย: task success rate, เวลาที่ใช้, ปัญหาที่เจอ
3. หาจุดที่ระบบ **ยังไม่เสถียร/ขัด** ก่อนเอาไปนำเสนอ
4. ตั้งคำถามสอบหัวข้อที่ตอบได้ด้วยผลทดสอบจริง (เช่น "ทดสอบ prototype แล้วพบว่าอะไร?")

## 2. กลุ่มตัวอย่างแนะนำ

| กลุ่ม | จำนวน | เหตุผล |
|---|---|---|
| เพื่อน/นักศึกษาที่เล่นแบดมือใหม่ | 2-3 คน | กลุ่มหลักของ "หาคู่เล่น + จองสนาม" |
| คนที่เล่นแบดประจำ (มือกลาง-เก่ง) | 1-2 คน | ตรวจลอจิก ระดับมือ/Court rule |
| เพื่อนรุ่นเดียวกัน (ไม่รู้โปรเจกต์) | 2 คน | ตรวจว่า UI งงไหม (cold start) |

รวม **5–7 คน** ก็เพียงพอสำหรับต้นแบบ (ไม่ต้องอิงสถิติ เพื่อนร่วมทีมช่วยจด)

## 3. เกณฑ์การนับสำเร็จ / ล้มเหลว

| Task | นับว่าสำเร็จเมื่อ |
|---|---|
| T1 สมัคร/ล็อกอิน | หาบัญชี demo ได้และเข้าได้ภายใน 2 นาที |
| T2 จองสนาม | ปักคอร์ตวันพรุ่งนี้ 19:00 ได้ ถูกขั้นตอน จบที่สถานะ "รอตรวจสอบ" |
| T3 ตรวจรายการของฉัน | เห็นรายการที่เพิ่งจอง และบอกสถานะได้ |
| T4 ยกเลิกการจอง | กดยกเลิกก่อนเริ่ม ≥ 2 ชม. และเห็นคอร์ตกลับว่าง |
| T5 ลงทะเบียนบุฟเฟต์ | ลงชื่อรอบ 19:00–22:00 ได้เลขคิวและเห็นสถานะ |
| T6 หาคู่เล่น + เชิญ | เลือกระดับมือตนเอง ผล match % และส่งคำเชิญได้ |
| T7 (admin) ยืนยันการจอง | เปลี่ยนเป็น "ยืนยันแล้ว" และรายได้ dashboard อัปเดต |
| T8 (admin) จัดสายแข่ง | เปิดหน้า tournament → สร้างสาย และเห็น Bracket |

**ตัวชี้วัด:** `% task success`, ปัญหาที่พบระหว่างทาง (พบครั้งละ ≥2 คน = ต้องแก้), เวลาเฉลี่ยต่อ task

## 4. บัญชีทดสอบที่เตรียมให้ผู้ใช้

| บัญชี | รหัส | บทบาท |
|---|---|---|
| customer01 | 123456 | ผู้เล่นมือใหม่ |
| player01 | player123 | ผู้เล่นมือกลาง-มีระดับแล้ว |
| admin | 12345 | ผู้ดูแล/ผู้จัด |

> **ก่อนเริ่ม:** ใช้ปุ่ม "ล้างข้อมูล (Clear)" ในหน้าการทดสอบ หรือ `localStorage.clear()` เพื่อให้ทุกคนเริ่มจากข้อมูลว่าง

## 5. คำถามหลังทำ Task (สั้นๆ 3 ข้อ/user)

1. "ขั้นตอนไหนรู้สึก งง/ไม่แน่ใจที่สุด?"
2. "ถ้าคุณจะจองสนามจริง คุณจะใช้อันนี้ไหม เพราะอะไร?"
3. "สมมติเราบอกว่านี่คือระบบที่พร้อมใช้ คุณจะไม่เชื่อเรื่องไหนเป็นพิเศษ?" ⭐ ข้อนี้จับจุดที่เราพูดเกินจริงในสไลด์

## 6. สิ่งที่ต้องเตรียมก่อนวันทดสอบ

- [ ] เบราว์เซอร์ (Edge/Chrome) ที่เปิด `index.html` จากเครื่องหรือผ่าน `file://`
- [ ] ตารางจดบันทึก task × ผู้ใช้ (ตามแบบในข้อ 3)
- [ ] ตัวจับเวลา (โทรศัพท์ก็ได้)
- [ ] กำหนดบทบาทในทีม: คนจด / คนควบคุมระบบ / คนถาม
- [ ] เตรียมผู้ใช้ demo 2 คน ที่มีระดับมือแล้ว (ผ่าน `auth/player-assessment.html`) เพื่อให้ T6 มีผลจริง

## 7. กำหนดสรุปผลที่ต้องส่งท้ายรอบ

```
ผู้ใช้: จำนวนที่สำเร็จ / รายการที่ล้มเหลว
Task success rate โดยรวม: __%
ปัญหาที่พบซ้ำ (≥2 คน): 1) ... 2) ...
ข้อ feedback ที่ตัดสินใจแก้ก่อนสอบ: ...
สิ่งที่ควรพูดในสไลด์ (พร้อมตัวเลขจริง): ...
```

---

## 8. สิ่งที่คาดว่าจะได้จากผล

- ถ้า **T2/T3 ต่ำกว่า 80%**: flow จองยังมีปัญหา → แก้ก่อนสอบหัวข้อ
- ถ้า **T6 ต่ำกว่า 70%**: หาคู่/เชิญซับซ้อน → ลดขั้นตอนหรือปรับข้อความ
- ถ้า **T8 ไม่ผ่านจาก admin**: เตรียมเพิ่มที่พำนัก/ผู้ช่วยทดสอบ หรือฝึกรอบ demo ให้เรียบร้อย
- คำตอบข้อ 3 ในส่วน 5 → ใช้เป็น **ขอบเขตที่ต้องถอยคำพูด** ในเล่ม (อย่า overclaim)
